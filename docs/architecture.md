Architecture
===================================

This document is short on purpose. For now it describes only the basic concept and it will grow together with the tool.


Concept
-----
offmain is a plugin for a transpiler. Developer adds it into the build of an application, it does not run on its own.

Code which should run in parallel is marked with directives. Directives are written as comments, so the source with directives is still valid JavaScript. The idea is taken from OpenMP: code is written sequentially and the directives say what should run in parallel.

During the build the plugin finds the directives and rewrites the marked code to run in Web Workers. Workers are separate threads without shared memory, they communicate with the main thread only through messages.


Parts
-----
- plugin (`src/plugin/`) - runs during the build and rewrites the marked code
- runtime library (`src/runtime/`) - runs in the browser, contains code which is the same for every input, rewritten code is connected to it

Output of the plugin is ordinary JavaScript, which is processed by the rest of the build chain.


Runtime library
-----
The library is a set of functions which do nothing on their own. It does not create workers and it does not know which tasks an application has. Code generated by the plugin creates the worker and gives both sides to the library.

- `connect(endpoint)` from `offmain/runtime` is for the calling side. It returns `run(task, args)`, which sends the call and returns a promise of the result.
- `serve(endpoint, tasks)` from `offmain/runtime/worker` is for the worker side. `tasks` is an object with functions, the key is the name of the task.

An endpoint is anything with `postMessage` and a `message` event: a `Worker`, the global scope of a worker or a `MessagePort`. Because of this the tests connect both sides with a `MessageChannel` and need no worker. A `MessagePort` has to be started with `start()` first, otherwise it delivers no messages.

A call is sent as `{ id, task, args }`. The answer is `{ id, ok: true, value }`, or `{ id, ok: false, error: { name, message } }` when the task throws. Calls are matched with answers by `id`, so more calls can be open at once. Arguments and results are copied by structured clone; a value which cannot be copied rejects the call.

Messages on both sides come from code generated by the plugin, so a wrong message means a bug in the tool, not in the application. The library checks for it only in a development build: a message with a wrong shape or an answer to a call which is not open throws `OffmainError`. The checks stand behind the constant `__OFFMAIN_DEV__`. The library does not define it, the plugin replaces it with `true` or `false` during the build, and with `false` the bundler can remove the checks as dead code. A call of a task which does not exist is rejected with `OffmainError` in both builds.
